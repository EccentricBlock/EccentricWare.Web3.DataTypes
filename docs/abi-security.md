# ABI security notes

Scope: the `EccentricWare.Web3.DataTypes.ABI` codec and its EVM adapters (`ABI.EvmAdapters`, `docs/abi-integration.md`). The codec answers one question: "are these bytes exactly one canonical encoding of this trusted schema, within my budgets?" It does not authenticate, authorise, resolve contract identity or understand what the values mean. Specification: sections 3, 9 and 10 of `docs/specs/ABI_DATA_Design_Specs.md`.

## Three separate guarantees (spec 3.1)

1. **Structure** (this codec): the whole document matches an immutable schema you supplied; for a call, the selector matches that schema's.
2. **Identity** (your registry data, held and enforced by `ContractFunctionResolver`; the code identities come from your host): `(chain, target, verified code or implementation identity, selector)` binds exactly one schema. A selector alone is a candidate, never a resolution: four-byte collisions exist, a public four-byte database is for offline suggestions only, and decoding successfully under a plausible schema proves nothing about the function that runs.
3. **Authorisation** (your policy and signer): transaction context, spending rules and the exact digest to be signed. `NestedCallWalker` enumerates the declared nested calls and asks your policy about each; it never decides that something is allowed.

## Threat model (spec 9.2) and controls

Inputs come from untrusted submitters; the attacker controls every byte. The schema, limits and registry are trusted. The attacker cannot change the buffer after validation unless the caller lets them.

**What the "Tests" column proves.** Codec rows are enforced and tested by the codec. Identity and nested-call rows are enforced by the EVM adapters (`ContractFunctionResolver`, `NestedCallWalker`, `RLPCalldataAdapter`) and tested against them; the registry CONTENTS, the code identities and the policy are the caller's, and the tests supply them as test data. The digest-binding row rests on a test-local signer (marked `IllustrativeFakes`): the library ships no signer.

## Signing-path contract

For any code that decides whether to sign:

1. **Resolve the schema from trusted metadata**, never from the transaction or a public selector database. A selector with no entry, or more than one, is a denial.
2. **Deny on every status other than `Success`.** Statuses explain a failure; they are not alternatives to try. Do not retry a non-canonical or trailing-data failure with a lenient parser.
3. **Accept only the strict canonical layout, and know it rejects more than Solidity does.** The deployed contract may accept a calldata layout this library refuses (gaps, overlapping or shared tails, trailing bytes, dirty padding or high bits). Such a transaction is denied here even though it would execute on chain. That is the specified compatibility policy (spec 2.3), and there is no permissive fallback. If your product must sign such transactions, that decision is yours and must not be made by loosening this codec inside a signing path; a separate, explicitly untrusted telemetry decoder cannot stand in for it.
4. **Treat `bytes` as opaque.** Traverse a `bytes` argument as a call only when verified contract metadata says it is one (an `ExecutionDescriptor` given to `NestedCallWalker`), with that child's own trusted schema, failing closed on anything unresolved. Neither the codec nor the walker proves that all internal EVM calls are visible in calldata.
5. **Use typed accessors, not raw words, and keep scale.** `TryGetUInt64` and `TryGetInt64` fail with `ValueOutOfRange` rather than truncating; fixed-point values come out as scaled words with their scale and are never an ordinary integer. A `string` is raw bytes until you ask for `TryGetStringUtf8Validated`, and a policy over text must run on exactly the validated bytes.
6. **Keep the bytes stable and bind the decision to them.** A `ReadOnlySpan<byte>` does not freeze its array. Create a stable per-request owner (copy once at ingress if mutation cannot be ruled out), validate and evaluate synchronously, and bind the approval to the exact signing message, request identity, chain, signer and policy version. If the bytes change, the trust result is void: re-run the whole decision. Repeating a field lookup on changed bytes is not a check. Async boundaries must hold the owner (`ReadOnlyMemory<byte>`) and rebuild the stack-scoped views inside synchronous code.
7. **Choose limits per trust level.** The defaults suit one call from an untrusted submitter; tighten them for anonymous input and size them to your protocol. Reject oversized input before allocating or hex-decoding.
8. **A decode is not an execution model.** The codec verifies ABI structure; it cannot validate the outer signature, nonce, chain id, sender, execution effects, token amounts or whether a call succeeds (spec 9.3).

`RLPCalldataAdapter` and `NestedCallWalker` (`docs/abi-integration.md`) apply these rules at the RLP envelope boundary and to nested calls.

## Behaviour worth knowing

- **Validation cost is paid once.** `TryDecodeComplete` is O(values + words examined). `TryLocate` and the accessors are O(path depth) and never rescan siblings (step-counter tests).
- **Error precedence is fixed** (docs/abi-api.md): invalid limits or null, size, selector, then the first structural error in depth-first declaration order, with limits reported where reached. Statuses are architecture independent.
- **Concurrent limits changes.** Limits are read once per call, so another thread rewriting a shared limits variable cannot split validation from frame sizing (`LimitsFlippedByAnotherThread_NeverCauseAnExceptionOrAWrongFrameBucket`).
- **Writers.** A struct copy of a writer shares all mutable state with the original (it cannot exceed a budget or hide a fault); a writer whose scratch was reused by a later `TryBegin` is dead. The scratch frames are caller-writable memory and are not trusted: corrupted or forged frames (random bytes, a byte copy of another writer's frames) are answered with `InvalidWriterState`, never an exception, and never a write outside the destination (`ABIWriterForgedScratchTests`). After any failure the destination holds no valid document.
- **No unchecked memory reads.** Every load in the codec is bounds-checked, the vector kernels included: `ABIWordRun.AllMasked128` and `AllMasked256` load `Vector.Create` on exact slices (until 2026-11-19 they used `Vector.LoadUnsafe`; switched by the owner's decision at a measured 4 to 10 percent on large static arrays, `docs/abi-design-notes.md` row 85). The guard-page over-read tests (`ABIWordRunGuardPageTests`: inputs end at the last byte of a page followed by a `PROT_NONE` page; Linux only, inconclusive elsewhere) remain as a backstop.
- **No constant-time claim.** Decode time depends on the input; do not use the codec to compare secrets.
- **Thread safety.** Compiled schemas are immutable and shared freely (`CompiledSchema_ReadsAreConsistentAcrossThreads`, `SharedSchemas_AreSafeUnderConcurrentWriters_*`). Views, writers, scratch and destinations are single-owner. Source definitions (`ABITupleDefinition`) are not thread safe while compiling.

## Checked arithmetic and CI

`Directory.Build.props` has an opt-in switch that compiles the whole library with C# overflow checking (`-p:RlpCheckedArithmetic=true`; the name predates ABI). Every deliberate wrap in the ABI code is inside `unchecked(...)`; every other `int`, `long` or `uint` overflow or narrowing cast throws `OverflowException` in that build, so a passing run proves no hidden overflow is reachable by the tests (not exhaustively). The property only matters when the library is **compiled**: force a rebuild whenever you switch, or stale binaries are reused and the run proves nothing.

```
dotnet build Eccentricware.Web3.DataTypes.Test -c Release --no-incremental -p:RlpCheckedArithmetic=true
RLP_EXPECT_CHECKED_BUILD=1 dotnet test Eccentricware.Web3.DataTypes.Test -c Release --no-build -p:RlpCheckedArithmetic=true --filter "FullyQualifiedName~Tests.ABI|FullyQualifiedName~CheckedArithmeticBuildGuardTests"
```

`RLP_EXPECT_CHECKED_BUILD=1` makes `CheckedArithmeticBuildGuardTests` (in the RLP tests, so the `Tests.ABI` filter alone does not run it) fail if the library was not built checked; add it to the filter, as below. Use the filter `~Tests.ABI`, **not** `~ABI`: `~ABI` is case-insensitive and also matches an unrelated `Address` test (`Parse_Unprefixed40HexWithoutZero_FamilyMatchesABigIntegerBase58Oracle_*`) that fails in a checked build because `Address.TryParseBare40Chars` is not checked-clean (`docs/abi-design-notes.md` row 16; pre-existing, not ABI). Rebuild unchecked afterwards (`dotnet build ... --no-incremental` without the property). `.github/workflows/ci.yml` runs the same two steps in its `checked-arithmetic` job for the RLP filter and, since the hardening work, for `Tests.ABI` plus the guard test.

## Verification

- Strict decoder, locator, accessors, schema compiler, selectors, writer, measurer and call encoder: the test classes listed in `docs/abi-conformance.md`.
- Independent evidence: Foundry `cast` fixtures, the Solidity documentation examples, a test-local reference model and a second independent encoder, and **Nethereum.ABI 7.1.0** (a test-only package, also a comparison baseline in the benchmark project; never referenced by the library). Nethereum's encoder agrees byte for byte with the reference encoder and the library writer on 250 random supported shapes and on every supported fixture, and its decoder reads the library's output as the same values (`ABINethereumDifferentialTests`). Its decoder is permissive, which is the compatibility gap above, not a defect of either side.
- Fuzz: `ABIFuzzTarget` (document, writer-script and schema-text entry points) replayed over about 1,900 seeds generated in memory by the tests (nothing generated is stored in the repository; the corpus folder holds only fuzzer-found inputs, none so far) plus seeded generative runs on every test run (`ABIFuzzCorpusReplayTests`; `Eccentricware.Web3.DataTypes.Test/ABI/Fuzz/Corpus/README.md`). **No coverage-guided fuzzer has run.**
- Independent reviews of the decoder and of the encoder: no functional defect; findings acted on are in `docs/abi-design-notes.md` rows 37, 44, 50 and 51. Reviews of the correction round (typed surface, vector kernels, scratch cut) are recorded in rows 64 to 77 of `docs/abi-design-notes.md`.
- Allocation: exact `GC.GetAllocatedBytesForCurrentThread` deltas after warm-up on success and failure paths (`ABIDecodeAllocationTests`, `ABIWriterAllocationTests`, `ABIHardeningAllocationTests`, and every fuzz input; they also pass in the Debug configuration). They depend on the JIT and runtime version; they pass on .NET 10.0.15 x64 Linux and have not run elsewhere.
- Runtime crash investigation: see "Unexplained runtime crash" below.

### Unexplained runtime crash

During the independent review of the decoder a multi-threaded harness (10 threads, deep schemas, public decode API) died intermittently with "Fatal error. Internal CLR error. (0x80131506)" in roughly 1 of 14 to 1 of 50 process launches (`docs/abi-design-notes.md` row 38). The hardening work tried to reproduce it with its own harness (library API only, random and mutated documents, decode, locate, accessors and all three encoders, 10 threads, with and without a memory-pressure thread and small gen0 budget, many process launches) and ran the equivalent harness over the RLP codec, whose validator uses the same `InlineArray` frame pattern. Result: 0 crashes in 200 launches of each codec (details and the limits of that evidence in `docs/abi-design-notes.md` row 52; the second hunt is row 67). It was **not reproduced and its cause is not established**; the absence of a crash is not evidence of its absence. A second hunt in the correction round, against the final code (which by then contained two unchecked vector kernels, `docs/abi-design-notes.md` row 66), ran the final review's own multi-threaded stress harness 100 times for 15 seconds (three launches at a time, about 1.27 billion mutate-and-decode iterations): again 0 crashes (row 67). It was equally clean with a `stackalloc` frame stack instead of the `InlineArray` tiers (also 100 launches), so that layout is not implicated by this evidence either. Anyone running the decoder under heavy multi-threaded load on another runtime or platform should treat an `ExecutionEngineException`-class fatal error as a runtime defect candidate and report it with the input.

## Default limits and where they meet

The defaults are policy, not wire rules. Three places where two defaults that look consistent meet are pinned by `ABIDefaultLimitSeamTests`; raise the named limit at the call site when the traffic needs it.

- **Compile static limit versus call size.** `ABICompileLimits.Default.MaxStaticEncodedBytes` (262,144) equals the decode `MaxEncodedBytes`, so `f(uint256[4096],uint256[4096])` compiles and its 262,144-byte argument document decodes as an `ABIData`, but as a call it is 262,148 bytes and `ABICallData.TryDecode` returns `InputTooLarge` (the limit covers the selector). Raise `MaxEncodedBytes` by at least 4 above the largest static schema you accept.
- **Compile depth versus decode depth.** The default compile depth is 32 (the hard cap) and the default `MaxValueDepth` for decoding and encoding is 16. This is the SPECIFIED seam, so it is kept: the table of spec 6.4 fixes `MaxSchemaDepth` at 32 "at compilation" and says "decoder runtime limit may be lower" (16 by default), and spec 6.1 fixes the 32-frame stack. Lowering the compile default to 16 would reject schemas the spec says must compile; the cost of the seam is that a schema accepted by compile can be unusable under the default decode until the caller raises `MaxValueDepth` (`docs/abi-design-notes.md`, row 76). A schema whose leaf sits at depth 17 to 32 compiles, but any non-empty document fails with `DepthLimitExceeded` until `MaxValueDepth` is raised (depth counts the root tuple as 1 and a primitive leaf as one more than its container). Real contracts need single digits (a Seaport order is 6).
- **Dynamic-array element limit.** `MaxArrayElements` is 4,096, so `uint256[4097]` and larger fail with `ElementLimitExceeded`. Ordinary mempool transactions stay under about 128 KiB (roughly 4,000 one-word elements), but return data and builder-included data can be larger. For a dynamic array of N one-word elements the budgets to raise are: `MaxArrayElements >= N`, `MaxEncodedBytes >= 64 + 32 * N` (+ 4 for a call), `MaxVisitedValues >= 2 + N` (default 16,384) and `MaxWorkUnits >= 4 + 2 * N` (default 100,000). Elements that are tuples or `bytes` cost more per element; the pinned numbers are in `ABIDecodeLimitsTests` and `ABIWriterLimitsTests`.

**Schema text parsing is bootstrap only.** `ABITupleDefinition.TryParse`, `TryCompileFunctionSignature` and the text overloads allocate in proportion to the length of the text (one definition per type, plus strings) before any compile limit can reject it. Array suffixes on one type are capped at the hard schema depth (more can never compile), so a hostile `[][][]...` costs a constant amount; very long tuples or names still cost memory proportional to their length. Never feed untrusted text or a JSON ABI to the parser on a request path; compile trusted schemas once at startup.

## What is not covered

Coverage-guided fuzzing, ARM64, Windows and macOS runs, a Solidity-harness differential, trim and Native AOT publish and full-policy latency measurement are listed in `docs/abi-conformance.md`.

**The EVM adapters are reference components, not a policy.** `RLPCalldataAdapter`, `ContractFunctionResolver`, `ExecutionDescriptor` and `NestedCallWalker` are shipped (spec 12 and 13). They do not fetch code identities, hold registry storage, verify descriptors, recover senders, compare the chain id with the served chain, or sign; those remain the caller's, and a wrong registry entry or descriptor defeats them. The walker sees only calls declared in calldata (spec 8.3).
